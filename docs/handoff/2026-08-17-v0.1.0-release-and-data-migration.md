## What happened, in order

1. **Release-readiness audit** found CI red on `main` (truncated `pnpm/action-setup` SHA in `ci.yaml`) + a stale `.env.example` claiming a non-existent `assert_production_config` guard.
2. **PR #96** (`fix/release-blockers-ci-cors`) → fixed the CI action SHA; corrected the CORS/env docs (the guard removal was a *deliberate design decision*, not an oversight — CORS is wide-open by design, mitigated by SameSite=Lax cookies + header API keys); wired `ENV`/`CORS_ORIGINS` into `compose.yaml` so `.env` overrides reach the container. Merged. CI green on `main`.
3. **PR #97** (`chore/jwt-and-name-cleanup`) → removed dead `JWT_SECRET` from `release.yaml`; fixed a real quickstart bug (`model="thai-citizen-guide"` is rejected 400 → `"onechat"`); updated name refs to "AI Chatbot Portal". Merged. CI green on `main`.
4. **Repo renamed** `thai-citizen-guide` → `chatbotportal`. Local `origin` remote updated; GitHub keeps the old URL as a redirect.
5. **Tag `v0.1.0`** pushed (first release; no prior tags). Triggered `release.yaml` on the self-hosted runner.
6. **The release succeeded — but against empty volumes.** The repo rename changed the runner's checkout directory (`thai-citizen-guide/` → `chatbotportal/`), and Docker Compose derives its **project name** from the directory. So the deploy created a *new* `chatbotportal` project with **empty volumes** — the backend ran migrations + seed on a blank DB. Old containers stopped (port conflict otherwise); old volumes (`thai-citizen-guide_*`) left intact.
7. **Operator migrated data** manually: `pg_dumpall` from the old `thai-citizen-guide_postgres_data` volume, restore into `chatbotportal_postgres_data`. Operator skipped the `COMPOSE_PROJECT_NAME` adopt path (chose clean `chatbotportal` naming instead).

## ⚠️ Durable fix pending — pin `COMPOSE_PROJECT_NAME` in `release.yaml`

**Root cause of the empty-volume deploy:** `release.yaml` runs `docker compose -f compose.yaml up` without an explicit project name, so Compose derives it from the checkout directory — which changed when the repo was renamed. **Every future tag deploy will target `chatbotportal_*` volumes now** (stable, since the repo won't be renamed again), but the deploy is still *fragile* to any future directory/repo-name change, and there's no guarantee the runner's `chatbotportal/` checkout persists across runner reinstalls.

**Fix (next PR):** add an explicit project name so the deploy is deterministic regardless of checkout dir. Since the operator migrated to `chatbotportal_*` volumes, pin to that:

```yaml
# .github/workflows/release.yaml — "Build and deploy" step
- name: Build and deploy
  env:
    COMPOSE_PROJECT_NAME: chatbotportal
  run: docker compose -f compose.yaml up -d --build --remove-orphans
```

This is a one-line, low-risk change. **Not yet done** — schedule as the next task.
